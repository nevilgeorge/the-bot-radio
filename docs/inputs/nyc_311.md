# 311, yesterday (`nyc_311_yesterday`)

Module: `src/the_bot_radio/services/inputs/nyc_311.py` (`Nyc311Service`).

## Source
- NYC Open Data, **"311 Service Requests from 2020 to Present"**, dataset id **`erm2-nwe9`**
  (checked against the Socrata catalog on 2026-10-26; the id `erm-2nwe-9e2v` returns
  `dataset.missing`). Pre-2020 data lives in `76ig-c548`, which we don't need.
- Endpoint: SODA 2.1 `GET https://data.cityofnewyork.us/resource/erm2-nwe9.json` with SoQL
  params. Works without auth. The SODA 3 `/api/v3/views/.../query.json` endpoint requires a token,
  so we don't use it.
- Auth: optional app token sent as the `X-App-Token` header, from `settings.nyc_open_data_app_token`
  (`NYC_OPEN_DATA_APP_TOKEN`). Without a token, requests share a throttled pool. That is fine at
  one run a day, but a token is recommended.
- ZIP: `settings.zip_code` (env `BOT_RADIO_ZIP`, default `11222`, Greenpoint).

## Queries (run concurrently)
1. Watermark, citywide: `$select=max(created_date) AS latest&$where=created_date >= '<D-2>T00:00:00'`
2. Grouped counts for D-2 and D-1 in one call:
   `$select=date_trunc_ymd(created_date) AS day, complaint_type, count(*) AS n`
   `&$where=incident_zip='11222' AND created_date >= '<D-2>T00:00:00' AND created_date < '<D>T00:00:00'`
   `&$group=day, complaint_type&$order=day, n DESC`

Here D = `ctx.run_date`. `created_date` is a **floating local (New York) timestamp** with no
offset. Citywide noise complaints peak at 22:00–23:59 in this field, which confirms it is local
time. Plain `YYYY-MM-DDT00:00:00` bounds therefore give a full ET day.

Latency: each query takes about 2–7s, and one cold run took 22s. The two run concurrently to stay
inside the 10s HTTP timeout and the 15s service timeout. An unbounded `max(created_date)` takes
over 60s, so always bound it.

## Update cadence and lag (observed 2026-10-26)
- The metadata says the dataset updates daily. `rowsUpdatedAt` was 2026-10-26 01:37 UTC
  (21:37 ET on the 25th), but the newest `created_date` was **2026-10-25T03:05**. Each nightly
  load only covers up to the early hours of that same day.
- So at the **06:00 ET run, yesterday is almost always incomplete** (about the first 3 hours,
  e.g. 16 rows vs. the usual ~110–130). D-2 is the newest complete day. Partial rows mean a
  "yesterday returned 0 rows" check would never fire, so staleness uses the watermark instead.

## Stale rule
- watermark ≥ D 00:00 (yesterday fully loaded): `ok`, report yesterday (0 rows gives `ok`, "0 requests").
- watermark ≥ D-1 00:00 (only D-2 complete): `stale`, report D-2 with a weekday prefix,
  e.g. `"Sat: 47 noise complaints"`. `data.date` = D-2, `data.requested_date` = yesterday.
  This is the normal case at 06:00.
- Otherwise, or if the watermark is null: `stale`, `"No data yet"`.
- A Socrata error object (a JSON dict instead of a list), HTTP errors, or bad rows raise an error,
  and the runner marks the input `skipped`.

## Value rule
Sum all complaint types whose name starts with "Noise" (case-insensitive; this covers
NYPD "Noise - Residential/Street/Commercial/Vehicle/Park" and DEP "Noise"). If that sum is > 0
and ≥ the largest single non-noise type, the value is `"N noise complaints"`. Otherwise it is
`"N requests"` (the total). In 11222, Illegal Parking (~40–60 a day) usually wins on weekdays and
noise wins on weekend nights.

## data
`date` (ISO day reported, or null), `requested_date` (yesterday), `zip`, `total`, `noise`,
`by_type` (top 10 `{type: n}`), `top_type` (the largest single raw type), `complete_through`
(the watermark). `raw` holds `latest` plus the grouped rows for the reported day.
